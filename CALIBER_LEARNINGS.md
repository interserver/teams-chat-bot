- **[correction]** Microsoft Teams' Markdown renderer ONLY visually nests bullets one level deep — `    - foo` (4-space indent) collapses back to the same depth as `- foo` in the rendered chat message, regardless of how many levels of indentation the source has. For deeper hierarchies, emit levels 2+ as plain text indented with **NBSPs (U+00A0)** plus a literal `- ` prefix (2 NBSPs per level baseline). NBSP is not Markdown whitespace, so the leading `- ` is rendered verbatim rather than parsed as a nested list marker, and Teams preserves the indent visually. See `bulletPrefix(level)` in `server/queue/notificationConsumer.js`.
- **[convention]** GitHub Actions check_run names use ` · ` (space-middledot-space, U+00B7) as the segment separator, not `/` or `-`. Three distinct patterns appear in practice and `decomposeCheckSegments` in `notificationConsumer.js` must handle all of them: `<Platform> · PHP X.Y · <lib>` (e.g. `Windows · PHP 8.3 · candy-core`), `<Phase> PHP X.Y · <lib>` where the PHP version is glued to the leading phase segment (e.g. `Test PHP 8.4 · candy-vt`), and `<prefix> (<variant>)` paren style. The PHP segment is matched by `/(PHP \d+\.\d+)/`; an embedded `PHP X.Y` inside a `·`-segment is split out into its own segment so all PHP X.Y siblings collapse under one bucket.

- **[env]** Notification routing has TWO independent repo-pattern envs that must be tuned together: `NOTIF_ANNOUNCE_REPOS` (comma-list of `owner/*` or exact `owner/repo` patterns that get redirected to `int-dev-announce`) and `NOTIF_ANNOUNCE_REPOS_EXCLUDE` (whitelist that EXEMPTS specific repos from the redirect, even when they would otherwise match). - **[gotcha]** Within a single notification-queue tick, if multiple trackable items in `processRoom`'s batch share the same `dedup_key`, they MUST NOT all call `handleTrackable` in parallel — `getRecent` returns empty for all but the first, so each spawns its own new activity and grouping silently breaks. Group by `dedup_key` first; for each group call `handleSingleNew` for `items[0]` (it awaits `saveRecent` before returning), then call `handleTrackable` sequentially (`await` each) for `items[1..]` so they find the cached entry. The naive `for (const it of trackable) await handleTrackable(...)` loop only works when each tick contains at most one event per SHA.
- **[pattern]** Better than the per-item sequential loop above: when N envelopes share a `dedup_key` in one tick, fold them in memory (`mergeGithubTrackable` is idempotent over `{header, items, header_identity}`) and issue ONE API call — `groupTrackableByDedup` → `canBatchMergeGroup` (msg type + matching `_commit_sha`) → `handleTrackableBatch` (recent lookup once, fold once, single `tryEdit` with `preMerged` option, fall back to `handleSingleNew` with `preMergedText`/`preMergedState`/`groupItems` if the edit fails). This reduces a 10-job CI burst from 10 edits to 1 edit. The `tryEdit(..., options.preMerged)` and `handleSingleNew(..., options.groupItems)` seams are how the batch path tells the per-item helpers "I already merged the content, you just need to send/edit and ack all the items I'm passing".
