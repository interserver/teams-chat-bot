- **[convention]** GitHub Actions check_run names use ` · ` (space-middledot-space, U+00B7) as the segment separator, not `/` or `-`. Three distinct patterns appear in practice and `decomposeCheckSegments` in `notificationConsumer.js` must handle all of them: `<Platform> · PHP X.Y · <lib>` (e.g. `Windows · PHP 8.3 · candy-core`), `<Phase> PHP X.Y · <lib>` where the PHP version is glued to the leading phase segment (e.g. `Test PHP 8.4 · candy-vt`), and `<prefix> (<variant>)` paren style (e.g. `render (candy-vcr)`). The PHP segment is matched by `/(PHP \d+\.\d+)/`; an embedded `PHP X.Y` inside a `·`-segment is split out into its own segment so all PHP X.Y siblings collapse under one bucket.
- **[gotcha]** `test/commands.test.js` has a long-standing failing test: `ticketQuick command "does not match unknown department"` at line 135 expects `null` but `ticketQuick.match('add foo ticket bar', ...)` returns `{ invalidDept: 'foo' }`. The other 70 tests pass and the failure pre-dates current work — don't treat it as a regression of your changes. Verify by stashing your changes and re-running before assuming you caused it.
- **[correction]** Microsoft Teams' Markdown renderer ONLY visually nests bullets one level deep — `    - foo` (4-space indent) collapses back to the same depth as `- foo` in the rendered chat message, regardless of how many levels of indentation the source has. For deeper hierarchies, emit levels 2+ as plain text indented with **NBSPs (U+00A0)** plus a literal `- ` prefix (2 NBSPs per level). NBSP is not Markdown whitespace, so the leading `- ` is rendered verbatim rather than parsed as a nested list marker, and Teams preserves the indent visually. See `bulletPrefix(level)` in `server/queue/notificationConsumer.js`.
- **[correction]** In Teams' NBSP deep mode, an indent step of 2 NBSPs per level is too narrow to visually distinguish depth 3 from depth 4 at a glance. Double the per-level step to 4 NBSPs (so depth 2 = 4 NBSPs, depth 3 = 8 NBSPs). Implementation: after building lines with the original prefix, doubling the leading NBSP run on each line before joining. **How to apply:** keep `bulletPrefix(level)` in sync with the test constants — when changing the per-level step, update `L2_DEEP`/`L3_DEEP` in `test/notificationConsumer.test.js` in lockstep.
- **[gotcha]** GitHub Actions emits one "skipped" check_run **per matrix cell** when a `strategy.matrix` job is gated out, AND it does NOT substitute the `${{ matrix.* }}` templates in the check_run's `name` — the literal template text leaks downstream. There are **two distinct failure modes**, and fixing one does not fix the other: (a) job-level `if:` evaluates false — fixed by moving the gate into a `build-matrix` prereq job emitting the matrix array (empty → zero cells spawn); (b) the job is `needs:` an upstream that fails (e.g. `needs: [test]` where `test` is a matrix with `fail-fast: false` — individual cell failures still mark the parent job failed → dependent is skipped via needs-failure BEFORE matrix evaluation → GitHub falls back to declared template names). The dynamic-matrix fix only suppresses placeholders when the matrix actually gets evaluated. Solution for (b): drop `needs: [<upstream>]` from any matrix job whose `name:` uses `${{ matrix.* }}` — let them run in parallel instead. See sugarcraft commit `c6c1121` (coverage + phpstan no longer `needs: [test]`).
- **[pattern]** Defensive bot-side net for the `${{ matrix.* }}` placeholder leak: `server/queue/filters.js`'s `shouldSkip()` returns the sentinel string `'__SILENT__'` for check_run / workflow_job events whose `name` contains literal `${{` text. The caller treats `__SILENT__` differently from `null` (pass through) and from `'<room>'` (redirect-with-label): it acks and drops without any log noise. Use this sentinel for any future class of envelope that is pure noise by construction — redirecting it to int-dev-announce would still be visible spam.
- **[convention]** When configuring per-repo room routing in `webhooks.interserver.net`'s `web/github.php` `pickRoom()`, keep upstream→downstream repo pairs in the SAME Teams room. The bot's action-triggered push attribution (`isActionTriggeredPush` → `findParentSha` → rewrite `dedup_key`) then looks up the trackable via `notif:recent:{room}:{dedup_key}` — trackable storage is **keyed by room**, so splitting the pair across rooms means the downstream push starts a new trackable instead of nesting under the parent commit. Default pair: `detain/sugarcraft` + `sugarcraft/*` (per `NOTIF_DOWNSTREAM_REPOS`). If you temporarily move one side for an experiment, move both sides together.
- **[gotcha]** Within a single notification-queue tick, if multiple trackable items in `processRoom`'s batch share the same `dedup_key`, they MUST NOT all call `handleTrackable` in parallel — `getRecent` returns empty for all but the first, so each spawns its own new activity and grouping silently breaks (this is the regression mode for "GitHub commit + job events used to group, now they don't"). Group by `dedup_key` first; for each group call `handleSingleNew` for `items[0]` (it awaits `saveRecent` before returning), then call `handleTrackable` sequentially (`await` each) for `items[1..]` so they find the cached entry. The naive `for (const it of trackable) await handleTrackable(...)` loop only works when each tick contains at most one event per SHA.
- **[convention]** When a status-bucket of leaves in `renderChecksGrouped` exceeds `LEAVES_COMPACT_THRESHOLD` (3), emit them as ONE comma-joined bullet via `leafCompact(ci)` instead of one bullet per leaf. `leafCompact` shortens `[details](url "title")` to `[d](url)` so a 30-package matrix run stays scannable. Keep new bucket emitters going through `emitLeafBucket(lines, level, leaves)` rather than open-coding the loop, otherwise the compaction won't apply to new groupings.
- **[pattern]** Action-triggered child pushes (CI workflow that commits + pushes back, or a subtree-sync workflow that pushes to downstream repos) arrive as brand-new `push` events on brand-new SHAs — GitHub gives no field linking them to the workflow_run that caused them. `notificationConsumer.js` bridges with two pieces: (1) `recordActiveWorkflow(env)` seeds a per-repo `notif:wfactive:{repo}` sorted set (member = parent SHA, score = ts, TTL = EDIT_WINDOW_MS) on every workflow_run/workflow_job/check_run; (2) `isActionTriggeredPush(env)` flags pushes whose pusher matches `github-actions[bot]`/`github-actions@`, sender ends in `[bot]`, head commit author email is a github-actions identity, OR the repo lives under a `NOTIF_DOWNSTREAM_REPOS` glob. For flagged pushes, `findParentSha(env)` looks up the most recent active parent SHA (own repo first, then any upstream from the map) and rewrites `extra._commit_sha`/`extra.dedup_key` so the push nests under the existing trackable. When adding a new bot-pusher repo, extend `NOTIF_DOWNSTREAM_REPOS` (or one of the regex tests in `isActionTriggeredPush`).
- **[gotcha]** Before assuming you broke notification grouping with a recent edit, check `git status` for **uncommitted** changes to `server/queue/notificationConsumer.js` — the bot is hot-reloaded by `nodemon` so an in-progress edit in your working tree is what's actually running in prod, even if the committed history looks clean. Run `git diff HEAD server/queue/notificationConsumer.js` first; the regression cause is almost always in the uncommitted diff, not in the last commit.
- **[gotcha]** Running `npm test` or `node --test 'test/*.test.js'` via the harness's Bash background runner consistently produces ZERO output even when subprocesses clearly started — the runner's `--test-isolation=process` interacts badly with the harness's task-output capture and the `.output` files stay 0 bytes. This is a *recurring* trap — every time you reach for `run_in_background: true` for tests, expect empty output and waste cycles polling. For reliable output, run a single file in the foreground with an explicit timeout: `node --test test/<file>.test.js 2>&1 | tail -25`. To run all four test files, list them explicitly on one foreground command rather than relying on glob expansion: `node --test test/commands.test.js test/botActivityHandler.test.js test/validateEnv.test.js test/notificationConsumer.test.js`.
- **[gotcha]** `TaskOutput` with `block: true` and a 60–120s timeout on a backgrounded `npm test` is ALSO useless — the task will report `status: "running"` with only `npm warn config production Use --omit=dev instead.` for the full block window and then return `retrieval_status: "timeout"`. Don't escalate from "`npm test` background returned empty" to "let me TaskOutput-block on it"; the underlying stdout capture is broken for that command, not just slow. - **[fix]** When `tryEdit` returns false due to `edit_skipped_no_convref`, the root cause is that the initial send went through `tryConstructedConvRef` (because the bot has never observed an inbound message in that channel) — so no real `convref:{conversationId}` was ever written to Redis. The lookup misses, the edit silently bails to `handleSingleNew`, and every subsequent event for the same trackable spawns its own top-level message. **Symptom:** PR / commit events that should nest under one trackable each appear as separate top-level Teams messages. **Fix:** `tryEdit` must also build a constructed ConversationReference via `buildConstructedConvRef(room, recent.conversationId)` rather than returning false when `loadConvRef` returns null. Emit `edit_using_constructed_convref` for trace visibility. Keep both send paths going through the same `buildConstructedConvRef` helper so they can't drift.

- **[gotcha]** `pull_request` event identity in `notificationConsumer.js`'s `prIdentity()` must be per-action+head_sha (`pr:{repo}:{number}:{action}:{headSha7}`), NOT per-PR. Using a single per-PR identity caused subsequent PR actions (opened → synchronize → closed) to all share the same id and the `incomingIdentity === headerIdentity` branch overwrote the header instead of appending a new bullet. The trackable is held together by `dedup_key=github:pr:{repo}:{number}` and `_commit_sha=pr:{repo}:{number}` (both PR-scoped) — the identity only decides which bullet *within* that trackable an event maps to. Bonus: re-delivery of the same webhook (same action + same head_sha) now safely overwrites itself in-place (idempotent) rather than spawning duplicates.

- **[correction]** When a sub-bullet for a PR action (e.g. `closed`) nests under a parent PR header (e.g. `opened`), only condense the sub-bullet to its first line if the parent already shows the PR description body. If the trackable's header was seeded by an unrelated event (e.g. a workflow_job firing first) OR the PR description was edited between actions, the verbose body must be preserved in the bullet so the reader sees it somewhere. - **[pattern]** GitHub `push`, `delete`, and `issue_comment` events have no direct webhook field linking them back to the PR they're conceptually part of. To make them nest under the PR's trackable, `notificationConsumer.js` keeps a `notif:prbranch:{repo}:{branch}` key (TTL = `EDIT_WINDOW_MS`) seeded by every `pull_request` event, then `attachPrContext(env)` rewrites `extra.dedup_key` and `extra._commit_sha` to the PR's scoped values (`github:pr:{repo}:{number}` / `pr:{repo}:{number}`) for: (a) `push`/`delete` on a branch in the index, (b) `issue_comment` whose `issue.pull_request` is set OR `issue.html_url` matches `/pull/{n}` (GitHub occasionally omits `issue.pull_request` even on PR comments — html_url is the reliable signal), (c) non-PR issue comments are still grouped onto `github:issue:{repo}:{number}` so multiple comments on the same issue coalesce. `attachPrContext` runs in `runTick` AFTER `normalizeGithubDedup` and BEFORE `isActionTriggeredPush`; the action-triggered branch must short-circuit when `dedup_key` already starts with `github:pr:` so PR routing isn't clobbered by parent-SHA attribution. **How to apply:** any new GitHub event type that should nest under a PR — `pull_request_review`, `pull_request_review_thread`, etc. — should add a branch to `attachPrContext` rather than open-coding the dedup_key rewrite at the call site.
- **[gotcha]** GitHub's `delete` webhook arrives with a producer-default message of the form `ℹ️ {sender} triggered a **delete** event on [{repo}](...)` — it doesn't actually say what was deleted. The `data` payload carries `ref` (the branch/tag name) and `ref_type` (`branch`|`tag`); rewrite `env.message` in `attachPrContext` to `🗑️ {sender} deleted {ref_type} \`{ref}\` in [{repo}](url)` when the original message matches the generic stub regex (`/triggered\s+a\s+\*?\*?delete\*?\*?\s+event/i`). Match on the stub so a future improvement to the producer side isn't clobbered. The rewrite happens regardless of whether the deleted ref maps to a known PR — even orphan deletes need the upgrade.
