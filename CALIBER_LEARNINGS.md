# Caliber Learnings

Accumulated patterns and anti-patterns from development sessions.

- **[gotcha]** `npm test` runs `node --test 'test/*.test.js'` — files must literally match that glob to be picked up. The glob is single-quoted so the shell does NOT expand it; node's test runner expands it internally. A bare `node --test test/` (no glob) silently produces no output in this repo. Always invoke `npm test` or `node --test test/<file>.test.js` for new test files; verify your new file's tests appear in the output count, not just that the command exits 0.
- **[gotcha]** Any JS regex character class containing multi-code-point emoji MUST use the `u` flag. Without it, JS treats the pattern as UTF-16 code units and surrogate halves match across unrelated emoji that share a high surrogate. Concrete trap: `/^[⏳🔄✅❌⏭️⚠️ℹ️❓]/` (no `u`) falsely matches text starting with 📦 because 📦 (U+1F4E6) and 🔄 (U+1F504) share the D83D high surrogate. Always write `/^[…emoji…]/u` and add a regression test that includes the lookalike emoji you do NOT want to match.
- **[pattern]** In `server/queue/notificationConsumer.js`, the trackable-message merge logic is exposed as the pure `mergeGithubTrackable(recent, env)` function and exported alongside `startConsumer`/`stopConsumer`/`runTick`. When changing how the header/items are assembled, modify that function and extend `test/notificationConsumer.test.js` rather than editing the merge code inline in `tryEdit()`. **Why:** the inline path was extracted specifically because it was untestable — keep it pure.
- **[convention]** The `recent` object persisted via `saveRecent(room, dedupKey, ...)` for trackable messages carries a structured `{ header, items: [{ identity, text }], header_identity }` alongside the legacy `text` / `commit_sha` / `appended_count` / `conversationId` fields. `mergeGithubTrackable` returns the same shape and also accepts a legacy plain-text string for `recent` (treated as the existing header). When adding new `saveRecent` call sites, persist the same field set or future edits will fall back to legacy string handling and lose structure.
- **[pattern]** For GitHub push events, the commit SHA used for dedup grouping in `normalizeGithubDedup` is `data.after` (or `data.head_commit?.id`), NOT `data.commits[0].id`. Commits arrive in chronological order so `commits[0]` is the OLDEST commit in the push, and downstream `check_run`/`workflow_job`/`status` events reference the HEAD (newest) SHA. Picking the wrong end of the array produces a dedup key that no later event will ever match → push and CI events fan out into separate messages.
- **[pattern]** All GitHub event types that carry a commit SHA (`push`, `workflow_job`, `workflow_run`, `check_run`, `check_suite`, `status`, `pull_request`, `pull_request_review`, `pull_request_review_comment`, `commit_comment`) MUST have their `extra.dedup_key` forcibly rewritten to `github:commit:{sha7}` in `normalizeGithubDedup`. PHP-set dedup keys are intentionally overridden so third-party CI bots (appveyor, etc.) and review activity merge into the same commit's trackable message.
- **[gotcha]** `test/commands.test.js` has a long-standing failing test: `ticketQuick command "does not match unknown department"` at line 135 expects `null` but `ticketQuick.match('add foo ticket bar', ...)` returns `{ invalidDept: 'foo' }`. The other 70 tests pass and the failure pre-dates current work — don't treat it as a regression of your changes. Fix it deliberately (either tighten `ticketQuick.match` to return null for unknown depts, or update the test) rather than as a side-effect.
- **[gotcha]** Running `npm test` or `node --test 'test/*.test.js'` via the harness's Bash background runner sometimes produces zero output even after the test runner clearly started subprocesses for each test file — the runner's `--test-isolation=process` interacts badly with the harness's task-output capture and the run wedges. For reliable output, run a single file in the foreground with an explicit timeout: `timeout 30 node --test test/<file>.test.js`. `npm test` does still work when invoked normally, just not from inside that background-task flow.
- **[pattern]** Every `saveRecent` call site that seeds a brand-new trackable (i.e. `handleSingleNew` and its `tryConstructedConvRef` fallback) MUST go through the `initialTrackableState(env)` helper, which runs `env.message` through `splitHeaderAndBullets` so the persisted `{ header, items, header_identity }` matches what `mergeGithubTrackable` would produce. **Why:** if you store the unsplit verbose `env.message` as `header` with `items: []`, the next re-delivery of the same event compares `splitHeaderAndBullets(incoming).headerText` (first line only) against the multi-line stored header, mismatches, and appends the entire event as a nested bullet → duplicated push with a sub-bullet of itself. **How to apply:** never write `header: env.message, items: []` literally — call `initialTrackableState(env)` and spread it.
- **[pattern]** The re-delivery dedup check inside `mergeGithubTrackable` compares the **first non-empty line** of the incoming `bulletMessage` against the **first non-empty line** of the stored `header`, NOT the full text on either side. This works whether the stored header is already split (header = first line, items hold commit list) or is still in legacy unsplit form from older Redis entries. Any rewrite of the re-delivery branch must preserve this two-sided first-line compare or existing legacy entries will start producing duplicate output.
- **[convention]** GitHub Actions check_run names use ` · ` (space-middledot-space, U+00B7) as the segment separator, not `/` or `-`. Two distinct naming patterns appear in practice and both must be handled by any decomposer: `<Platform> · PHP X.Y · <lib>` (e.g. `Windows · PHP 8.3 · candy-core`) and `<Phase> PHP X.Y · <lib>` where the PHP version is glued to the leading phase segment (e.g. `Test PHP 8.4 · candy-vt`). The PHP segment is matched by `/(PHP \d+\.\d+)/`; everything before it is the platform/phase, everything after is the lib.

- **[convention]** GitHub Actions check_run names use ` · ` (space-middledot-space, U+00B7) as the segment separator, not `/` or `-`. Three distinct naming patterns appear in practice and `decomposeCheckSegments` in `notificationConsumer.js` must handle all of them: `<Platform> · PHP X.Y · <lib>` (e.g. `Windows · PHP 8.3 · candy-core`), `<Phase> PHP X.Y · <lib>` where the PHP version is glued to the leading phase segment (e.g. `Test PHP 8.4 · candy-vt`), and `<prefix> (<variant>)` paren style (e.g. `render (candy-vcr)`). The PHP segment is matched by `/(PHP \d+\.\d+)/`; an embedded `PHP X.Y` inside a `·`-segment is split out into its own segment so all PHP X.Y siblings collapse under one bucket.
- **[correction]** Microsoft Teams' Markdown renderer ONLY visually nests bullets one level deep — `    - foo` (4-space indent) collapses back to the same depth as `- foo` in the rendered chat message, regardless of how many levels of indentation the source has. For deeper hierarchies, emit levels 2+ as plain text indented with **NBSPs (U+00A0)** plus a literal `- ` prefix (2 NBSPs per level). NBSP is not Markdown whitespace, so the leading `- ` is rendered verbatim rather than parsed as a nested list marker, and Teams preserves the indent visually. See `bulletPrefix(level)` in `server/queue/notificationConsumer.js` (level 1 = real Markdown bullet `- `, level 2+ = `NBSP*(level-1)*2 + '- '`). **Why:** the user directly reported "teams is only showing 1 level of bullet nesting" after a multi-level Markdown tree was deployed. **How to apply:** any new multi-level outline emitted into Teams text must follow this convention — pure-Markdown indentation will visually flatten.
- **[pattern]** When you need to verify that a source file actually contains a non-printable character like NBSP (U+00A0, bytes `c2 a0`) rather than a regular space, use `sed -n '<line>p' file | xxd | head -2`. Eyeballing the file in an editor won't tell you whether `' '` is space or NBSP. Especially important after `Edit` operations that paste NBSP-containing strings, since the harness preserves them but the bytes are not visually distinguishable.
- **[gotcha]** When changing the indentation convention used by `renderTrackable` / `bulletPrefix` / `indentAsBullet`, the existing assertions in `test/notificationConsumer.test.js` that match against `' - '` / `'  - '` literals will all silently break because the prefix bytes change. Centralise the prefixes in the test file (`const L1 = '- '; const L2 = NBSP+NBSP+'- '; ...`) and reference them from every assertion so a future indentation switch needs only one edit. Mixing literal `'  - '` (ASCII spaces) with the actual NBSP-prefixed output produces zero matches and the failure message just looks like generic "text doesn't contain expected string".

- **[pattern]** Teams rendering has two distinct depth regimes that need different output strategies: (1) **Shallow** (max depth 2) — use native Markdown nested bullets with ASCII-space indentation, joined with plain `\n`; Teams renders each list item on its own row natively. (2) **Deep** (depth 3+) — use NBSP-indented literal `- ` text on every level-2+ line, AND join with `'  \n'` (CommonMark hard break) so each NBSP-text line gets its own row instead of collapsing into paragraph continuation. Detect by scanning for any line starting with the depth-3 prefix; choose the rendering mode for the entire message accordingly. **How to apply:** any new Teams-bound multi-level renderer should follow this same dual-mode pattern — testing only the shallow case will let deep-mode regressions ship.
