For reliable output, run a single file in the foreground with an explicit timeout: `timeout 30 node --test test/<file>.test.js`.
- **[pattern]** Every `saveRecent` call site that seeds a brand-new trackable (i.e. `handleSingleNew` and its `tryConstructedConvRef` fallback) MUST go through the `initialTrackableState(env)` helper, which runs `env.message` through `splitHeaderAndBullets` so the persisted `{ header, items, header_identity }` matches what `mergeGithubTrackable` would produce. **Why:** if you store the unsplit verbose `env.message` as `header` with `items: []`, the next re-delivery compares first-line vs multi-line, mismatches, and appends the whole event as a sub-bullet. **How to apply:** never write `header: env.message, items: []` literally — call `initialTrackableState(env)` and spread it.
- **[pattern]** The re-delivery dedup check inside `mergeGithubTrackable` compares the **first non-empty line** of the incoming `bulletMessage` against the **first non-empty line** of the stored `header`, NOT the full text. This works whether the stored header is split or in legacy unsplit form. Any rewrite of the re-delivery branch must preserve this two-sided first-line compare or existing legacy entries will start producing duplicate output.
- **[convention]** GitHub Actions check_run names use ` · ` (space-middledot-space, U+00B7) as the segment separator, not `/` or `-`. Three distinct patterns appear in practice and `decomposeCheckSegments` in `notificationConsumer.js` must handle all of them: `<Platform> · PHP X.Y · <lib>`, `<Phase> PHP X.Y · <lib>` where PHP version is glued to the leading segment (e.g. `Test PHP 8.4 · candy-vt`), and `<prefix> (<variant>)` paren style (e.g. `render (candy-vcr)`). The PHP segment is matched by `/(PHP \d+\.\d+)/`; an embedded `PHP X.Y` inside a `·`-segment is split out into its own segment.
- **[correction]** Microsoft Teams' Markdown renderer ONLY visually nests bullets one level deep — `    - foo` (4-space indent) collapses back to the same depth as `- foo`. For deeper hierarchies, emit levels 2+ as plain text indented with **NBSPs (U+00A0)** plus a literal `- ` prefix. NBSP is not Markdown whitespace, so the leading `- ` is rendered verbatim rather than parsed as a nested list marker. See `bulletPrefix(level)` in `server/queue/notificationConsumer.js`.
- **[correction]** In Teams' deep-mode NBSP-indented rendering, the lines are paragraph-continuation of the enclosing level-1 list item — Markdown joins continuation lines with a single space, so without a hard break they all collapse onto one line in Teams (`  - **Windows**   - ✅ PHP 8.3 Check success     - candy-shine (…)`). Fix: join deep-mode lines with `'  \n'` (two trailing spaces + newline) which is CommonMark's hard line break. Shallow mode keeps plain `\n` since each real Markdown list item already gets its own row natively. **Why:** the user reported nested bullets showing up all on one line after the initial NBSP indentation switch.
- **[correction]** In Teams' NBSP deep mode, an indent step of 2 NBSPs per level is too narrow to visually distinguish depth 3 from depth 4 at a glance (2 vs 4 char widths look similar). Double the per-level step to 4 NBSPs (so depth 2 = 4 NBSPs, depth 3 = 8 NBSPs). Implementation: after building lines with the original prefix, doubling the leading NBSP run on each line before joining. **Why:** the user reported "the 4th level of indent or w/e is barely noticable from the 3rd.. it needs a bit more indented". **How to apply:** keep `bulletPrefix(level)` in sync with the test constants — when changing the per-level step, update `L2_DEEP`/`L3_DEEP` in `test/notificationConsumer.test.js` in lockstep.
- **[pattern]** When you need to verify that a source file actually contains a non-printable character like NBSP (U+00A0, bytes `c2 a0`) rather than a regular space, use `sed -n '<line>p' file | xxd | head -2`. Eyeballing the file in an editor won't tell you whether `' '` is space or NBSP. Especially important after `Edit` operations that paste NBSP-containing strings.
- **[gotcha]** When changing the indentation convention used by `renderTrackable` / `bulletPrefix` / `indentAsBullet`, existing assertions in `test/notificationConsumer.test.js` that match against `' - '` / `'  - '` literals will silently break because the prefix bytes change. Centralise the prefixes in the test file (`const L1 = '- '; const L2_SHALLOW = '  - '; const L2_DEEP = NBSP.repeat(N) + '- '; ...`) and reference them from every assertion so a future indentation switch needs only one edit.
- **[pattern]** When debugging the notification consumer's render output, drive `mergeGithubTrackable` directly from a one-liner `node -e "..."` script that constructs the minimal envelope shape and chains multiple calls (each merging the previous `recent` with a new env). Faster than spinning up the full consumer + Redis. Example envelope: `{ type: 'msg', message: '...', extra: { event_type: 'check_run', _commit_sha: '<sha7>', dedup_key: 'github:commit:<sha7>', data: { check_run: { name, status, html_url } } } }`. When visualising NBSP-indented output, pipe through `.replace(new RegExp(NBSP,'g'),'▫')` so the structure is visible in a terminal that otherwise renders NBSPs as plain spaces. To see CommonMark hard breaks, also `.replace(/  \n/g, '⏎\n')`.
- **[pattern]** Teams rendering has two distinct depth regimes that need different output strategies: (1) **Shallow** (max depth 2) — use native Markdown nested bullets with ASCII-space indentation, joined with plain `\n`; Teams renders each list item on its own row natively. (2) **Deep** (depth 3+) — use NBSP-indented literal `- ` text on every level-2+ line, AND join with `'  \n'` (CommonMark hard break) so each NBSP-text line gets its own row instead of collapsing into paragraph continuation. Detect by scanning for any line starting with the depth-3 prefix; choose the rendering mode for the entire message accordingly. **How to apply:** any new Teams-bound multi-level renderer should follow this same dual-mode pattern — testing only the shallow case will let deep-mode regressions ship.

- **[gotcha]** GitHub Actions emits one "skipped" check_run **per matrix cell** when a `strategy.matrix` job is gated out by a job-level `if:`, AND it does NOT substitute the `${{ matrix.* }}` templates in the check_run's `name`. The literal template text leaks downstream — e.g. webhook consumers receive a check_run literally named `Coverage · ${{ matrix.lib }}`. Detect by seeing `${{ matrix.* }}` placeholders surfacing in Teams / Slack / consumers. **Fix:** move the gate out of the job and into the matrix itself — create a `build-matrix` prereq job that emits the lib/php list as a JSON output (or `[]` when the gate is closed), then have the matrix job consume it via `matrix: ${{ fromJSON(needs.build-matrix.outputs.foo) }}`. Empty matrix → zero jobs spawn → zero skipped placeholders. See `/home/sites/sugarcraft/.github/workflows/ci.yml` commit `f813532` for the canonical example covering both single-axis (`lib`) and multi-axis (`php` + `lib`) matrices.
- **[pattern]** Action-triggered child pushes (e.g. a CI workflow that commits + pushes back to master, or a subtree-sync workflow that pushes to downstream repos) arrive as brand-new `push` events on brand-new SHAs — GitHub gives no field linking them to the workflow_run that caused them. `notificationConsumer.js` bridges that gap with two pieces: (1) `recordActiveWorkflow(env)` seeds a per-repo `notif:wfactive:{repo}` sorted set (member = parent SHA, score = ts, TTL = EDIT_WINDOW_MS) on every workflow_run/workflow_job/check_run; (2) `isActionTriggeredPush(env)` flags pushes whose pusher matches `github-actions[bot]`/`github-actions@`, whose sender ends in `[bot]`, whose head commit's author email is a github-actions identity, OR whose repo lives under a `NOTIF_DOWNSTREAM_REPOS` glob. For flagged pushes, `findParentSha(env)` looks up the most recent active parent SHA (own repo first, then any upstream from the map) and the consumer rewrites `extra._commit_sha`/`extra.dedup_key` so the push nests under the existing trackable. Default downstream map: `detain/sugarcraft:sugarcraft/*`. When adding a new bot-pusher repo, extend `NOTIF_DOWNSTREAM_REPOS` (or one of the regex tests in `isActionTriggeredPush`) rather than special-casing in the merger.
- **[convention]** When a status-bucket of leaves in `renderChecksGrouped` exceeds `LEAVES_COMPACT_THRESHOLD` (3), emit them as ONE comma-joined bullet via `leafCompact(ci)` instead of one bullet per leaf. `leafCompact` shortens `[details](url "title")` to `[d](url)` so a 30-package matrix run stays scannable. The threshold and helper live next to `leafInline`/`leafOnly` in `notificationConsumer.js` — keep new bucket emitters going through `emitLeafBucket(lines, level, leaves)` rather than open-coding the loop, otherwise the compaction won't apply to new groupings.

- **[gotcha]** GitHub Actions emits one "skipped" check_run **per matrix cell** when a `strategy.matrix` job is gated out, AND it does NOT substitute the `${{ matrix.* }}` templates in the check_run's `name` — the literal template text leaks downstream. There are **two distinct failure modes**, and fixing one does not fix the other: (a) job-level `if:` evaluates false — fixed by moving the gate into a `build-matrix` prereq job emitting the matrix array (empty → zero cells spawn); (b) the job is `needs:` an upstream that fails (e.g. `needs: [test]` where `test` is a matrix with `fail-fast: false` — individual cell failures still mark the parent job failed → dependent is skipped via needs-failure BEFORE matrix evaluation → GitHub falls back to declared template names). The dynamic-matrix fix only suppresses placeholders when the matrix actually gets evaluated. Solution for (b): drop `needs: [<upstream>]` from any matrix job whose `name:` uses `${{ matrix.* }}` — let them run in parallel instead. See sugarcraft commit `c6c1121` (coverage + phpstan no longer `needs: [test]`).
- **[pattern]** Defensive bot-side net for the `${{ matrix.* }}` placeholder leak: `server/queue/filters.js`'s `shouldSkip()` returns the sentinel string `'__SILENT__'` for check_run / workflow_job events whose `name` contains literal `${{` text. The caller treats `__SILENT__` differently from `null` (pass through) and from `'<room>'` (redirect-with-label): it acks and drops without any log noise. Use this sentinel for any future class of envelope that is pure noise by construction — redirecting it to int-dev-announce would still be visible spam.
- **[convention]** When configuring per-repo room routing in `webhooks.interserver.net`'s `web/github.php` `pickRoom()`, keep upstream→downstream repo pairs in the SAME Teams room. The bot's action-triggered push attribution (`isActionTriggeredPush` → `findParentSha` → rewrite `dedup_key`) then looks up the trackable via `notif:recent:{room}:{dedup_key}` — trackable storage is **keyed by room**, so splitting the pair across rooms means the downstream push starts a new trackable instead of nesting under the parent commit. Default pair: `detain/sugarcraft` + `sugarcraft/*` (per `NOTIF_DOWNSTREAM_REPOS`). If you temporarily move one side for an experiment, move both sides together.
- **[gotcha]** Within a single notification-queue tick, if multiple trackable items in `processRoom`'s batch share the same `dedup_key`, they MUST NOT all call `handleTrackable` in parallel — `getRecent` returns empty for all but the first, so each spawns its own new activity and grouping silently breaks (this is the regression mode for "GitHub commit + job events used to group, now they don't"). Group by `dedup_key` first; for each group call `handleSingleNew` for `items[0]` (it awaits `saveRecent` before returning), then call `handleTrackable` sequentially (`await` each) for `items[1..]` so they find the cached entry. The naive `for (const it of trackable) await handleTrackable(...)` loop only works when each tick contains at most one event per SHA.

- **[gotcha]** Before assuming you broke notification grouping with a recent edit, check `git status` for **uncommitted** changes to `server/queue/notificationConsumer.js` — the bot is hot-reloaded by `nodemon` so an in-progress edit in your working tree is what's actually running in prod, even if the committed history looks clean.
